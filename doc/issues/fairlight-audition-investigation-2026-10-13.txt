Fairlight Media Pool audition investigation - 2026-10-13

Status
------
No root cause is proven. The initial investigation used a standalone Qt probe
and static inspection without implementation changes or Resolve attachment.
Later sections record the child-host diagnostic and deeper read-only binary
analysis on the Xeon. Builds 004 and 005 did not fix audio.
The installed Resolve executable inspected here reports version 21.1.1.10.
The current source retains the unsuccessful 005 parent-connection experiment;
it must not be mistaken for a confirmed fix.

Current conclusion
------------------
The child-host experiment on the Xeon subsequently succeeded: transferred
audition content remaining in the original main window plays audible audio,
updates its waveform smoothly, shows Control Room metering and switches playback
with the timeline normally. This narrows the investigation to the separate-window
context or associated window setup, rather than layout transfer alone. It does
not yet identify a specific Resolve check or registration step.

The best-supported description of the separate-window failure is a failed playback handoff: floating audition
enters a visual playback state and freezes timeline indicators, but does not
stop the running timeline or become audible. The failing internal call or
condition is not known. Investigation should target coordination between
audition transport, timeline transport and active audio-source selection.

Observed in Resolve (reported by Wolfgang)
------------------------------------------
1. Docked Media Pool audition produces audible audio and Control Room meter
   signal. Undocked audition has working transport and waveform movement but
   neither audible audio nor Control Room meter signal.
2. Returning to the docked context and requesting playback restores audio;
   docking alone during active failed audition does not (see Xeon observations).
3. Turning the native Media Pool toggle back on while floating does not help.
4. Build 004 never turned that toggle off during detachment/restoration. It
   remained silent, so the automatic off transition is not necessary to fail.
5. Build 005 attached the floating Qt window to the original slot. It remained
   silent, so an intact parentWidget chain alone is insufficient.
6. Starting floating audition and clicking an empty part of Resolve's main
   window does not restore audio or meter signal. A simple foreground-main-
   window requirement is therefore a weaker explanation.

The initial inference that silence and stationary meters locate a break before
the Control Room meter is not established. The later observations below show
that the meter displays can freeze while timeline audio continues normally.

Later concurrent-playback observation (supersedes the meter inference above)
--------------------------------------------------------------------------
With timeline playback already running, starting the floating audition player
moves its waveform but freezes the main timeline playhead and the Bus 1,
Control Room and Loudness meter displays. Timeline audio AND the viewer image
continue playing. Stopping audition immediately restores the main playhead and
meter updates, without an audio glitch.

Therefore, a stationary Control Room meter cannot by itself establish that no
audition samples reach a particular point in the engine. Its display may not be
updating. The audible absence of audition remains a separate observation.
Nor is this a complete GUI-thread stall: the audition display and timeline
viewer still update. Selected display subscriptions, playback UI modes, or
selective update suppression are better candidates than a general GUI freeze.

This strengthens a split-state hypothesis: audition playback changes a shared
UI/transport state while the engine continues timeline playback and does not
make the expected audible audition transition. That can explain both a moving
audition waveform and frozen timeline indicators without requiring the timeline
engine to stop. It is not yet established whether the state is an active-player
selection, a signal subscription, an update-suppression flag, or another shared
playback controller.

Docked baseline (subsequently confirmed by Wolfgang)
---------------------------------------------------
With timeline playback running, starting docked audition stops the timeline and
seamlessly starts audible audition playback. Stopping audition leaves the
timeline stopped; it does not resume previous timeline playback.

                                Docked audition       Floating audition
Timeline on audition start      Stops                 Keeps playing A/V
Timeline playhead and meters    Stop with timeline    Freeze despite playback
Audition waveform              Moves                 Moves
Audition audio                 Audible               Silent
Timeline on audition stop      Remains stopped       Continues; indicators resume

This isolates a playback-handoff failure more precisely than the original
description of lost audition audio. Some shared UI state responds to audition
start/stop while the expected timeline-stop/audio-source transition does not.
That is a behavioral inference, not proof of a particular internal API failure.

Extend the proposed trace to include timeline transport state and indicator
updates at audition start/stop, not only at detach/dock. Compare the identical
sequence docked and floating. Track player identity on each transport event,
IsActiveChanged and MuteAudioChanged where available, and whether main playhead
and meter objects still receive update events. Sample this with bounded
instrumentation; do not add unbounded frame-by-frame logging or playback polling.

Xeon workstation: docking during active audition (2026-10-13)
-----------------------------------------------------------
Wolfgang tested on the Intel Xeon E5-2687W v4 workstation where the recurring
Unbound discovery scan had previously caused playback stalls and was removed.
Floating Fairlight Media Pool audition is silent here too, but its moving
waveform is choppy/stuttery; on the Ryzen system the floating waveform was smooth.

Docking while audition continues does NOT immediately recover playback:
  - waveform movement remains choppy/stuttery;
  - audition remains inaudible;
  - the Control Room meter shows no audition signal.
Stopping audition in that now-docked pane and starting it again restores all
three together: smooth waveform movement, audible audition and active Control
Room meter display.

Subsequent refinement from Wolfgang: an explicit Stop is NOT required. After
docking the still-visually-playing, failed audition, clicking its Play button
again also restores normal playback. Whether Resolve internally stops/restarts
or reinitializes transport on that Play request is not known.

The reverse transition was also tested: start audition while docked (normal
audio and waveform), then undock without manually stopping. Undocking stops
audition playback. Thus successful docked playback does not simply carry on in
the floating host. The exact detachment step or event causing the stop has not
been identified.

This qualifies the earlier statement that docking restores audio: docking alone
does not recover an already-running failed audition. A new Play request in the
docked context suffices, with no explicit Stop required. It has not yet been
established whether pressing Play again while still floating can recover it.

Inference: handling of a Play request in its current widget/window context
deserves particular attention, alongside the stop triggered during detachment.
Restoring widget placement alone is not sufficient to recover the active
playback state. These observations do not identify a particular internal
registration, audio-routing or scheduling mechanism, or prove both transitions
fail at the same internal step.
Smooth but silent floating audition on Ryzen also shows that waveform stutter
is not necessary for the audio failure; a common cause remains possible.
Meter inactivity remains display evidence, not proof of an engine signal path.

Extend checkpoint comparisons with floating start -> dock without stopping ->
Play again, and docked start -> undock -> stopped. Record these transitions
separately, rather than treating docking and the subsequent Play request as one
recovery event. Do not assume an explicit Stop is necessary for recovery.

Spacebar transport targeting: docked versus floating (2026-10-13)
---------------------------------------------------------------
Wolfgang reports that docked playback targeting follows the clicked area:
  - click the main timeline, then Space: timeline playback toggles;
  - click docked Media Pool, then Space: audition playback toggles.
With Media Pool undocked, Space toggles the main timeline even after clicking
inside the floating Media Pool. Clicking that pane does not make audition the
spacebar playback target.

This is behavioral evidence of lost audition transport targeting in the floating
context. It strengthens the player recognition/active-context hypothesis when
considered alongside the failed timeline-to-audition handoff. It does not prove
that a single active-player registry controls both keyboard dispatch and audio.
Qt focusWidget/activeWindow, shortcut ownership/context and Resolve's logical
player selection have not been traced; a clicked pane is not itself a measured
focus state. A window-scoped shortcut path could explain the keyboard symptom
without independently explaining the silence.

The next bounded trace should therefore compare clicking the timeline, clicking
docked audition, and clicking floating audition, then requesting playback by
Space versus the audition Play button. Capture actual focus/window identities
and verified player focus/active/transport signals at those checkpoints. Do not
work around this by forwarding Space or synthesizing focus: that could mask the
targeting symptom while leaving the failed audio handoff unchanged.

The actual operation is broader than reparenting one splitter
------------------------------------------------------------
The snapshot has frameAudioPanelMediaPoolContainer -> mediaPoolSplitter ->
frameAudioPagePreviewPlayerContainer -> previewPlayer (UiPlayerWidgetImp).
The player's direct parent remains unchanged during our transfer.

SidebarFloatSession::start creates a PaneFloatingWindow; in 005 only, it gives
that host the original slot as its QWidget parent with Qt::Window flags.
It copies the icon/taskbar identity, sets geometry/title, and calls
host->setLayout(originalLayout). Fairlight does NOT use preserveNativeLayout:
that option is currently enabled only for Color.

Consequently both the original QLayout and its managed splitter change parent.
The original slot receives a new placeholder layout. Any cached pointer to the
original layout now refers to a layout owned by the floating host, while
slot->layout() returns a different object. The host is then shown, and normally
the native Media Pool toggle is clicked off. Restored geometry and startup fade
may also apply. Native window creation occurs when platform helpers use winId().
We have no evidence that native child handles are actually recreated in this
Resolve subtree; that must be measured rather than assumed.

Important correction to the reasoning behind 005: QWidget::isAncestorOf checks
membership within one window and stops at a window boundary. A parented Qt

player->window(). Also, the shown probe reports isVisibleTo(page)==true even
across the window boundary; it must not be treated as equivalent to isAncestorOf.

An existing cross-object signal connection delivered once after every transfer.
Neither our transfer code nor the Qt reparent path intrinsically requires
disconnecting the player's signals. Resolve's own event handlers could still
change subscriptions or routing; this probe cannot establish what they do.

Ranked explanations
-------------------
1. Player recognition/registration depends on the original window or same-window
   ancestry. A window() comparison/cast, isAncestorOf test, or window-scoped
   active-player registry would fail in both 004 and 005 and recover on docking.
   Clicking the main window would not repair the player's window identity.
   The later spacebar observation also fits lost audition transport targeting
   across the window boundary. Later static analysis confirmed isAncestorOf in
   Resolve's focus-context lookup (see below); its role in the actual failing
   audio handoff has not been traced. Shortcut dispatch may be a separate path.

2. Resolve responds to hide/reparent/window transitions by unregistering or
   deactivating the audition source, and normal show/focus handling does not
   reactivate it in an unfamiliar host. This also fits all observations. A
   stopped visual transport is not required for separate audio deactivation.

3. The moved native layout, direct-parent expectations around the splitter, or
   context lookup through its old slot breaks an audio-specific lookup. 005
   retains an ancestor chain but does not retain the splitter's immediate parent
   or the original layout's owner. This has not been isolated by either build.

4. Native window/surface identity is used by player/audio integration. Qt can
   change native parenting or effective window handles. Possible, but there is
   presently no handle trace or evidence of an HWND-bound audio endpoint.

Weaker explanations: automatic toolbar reclamation (004 rules it out as a
necessary trigger), absence of all QObject ancestry (005), simple main-window
foreground state (user test), generic automatic Qt signal disconnection (probe
and source), and a pure speaker-device failure (docking plus meter observations).

Observed native flow from imported Qt calls and operand tracing:
  PopOutPlayer hides the original container (+0x310), removes the video player
  from its original QLayout (+0x318), passes it to a dedicated host (+0xd0),
  shows that host and performs additional player/helper calls.
  Host insertion at 0x144f7fc10 sets an internal byte, adds the widget to the
  host's QBoxLayout and calls another player helper.
  DockPlayer hides the host, removes that same player from its layout, adds it
  back to the original QBoxLayout, shows the original container and performs
  additional player/helper calls. Removal helper is at 0x144f7fe00.
The additional internal calls have not all been named or decoded. Do not infer
that they register audition audio. These slots take no player argument and are
not a general-purpose detach/reattach API for the audition widget.

Stronger lead: Resolve's own focus-context lookup uses same-window ancestry.
  UiFocusedWidgetManager metadata: 0x15b0c4510.
  Its metaObject virtual at 0x144f90c00 returns that metadata; the same QObject
  vtable contains its eventFilter at 0x144f90900 (vtable entry 0x148822350).
  FocusChanged is a signal with signature FocusChanged(int,int), whose parameter
  names are p_OldFocusWidget and p_NewFocusWidget. These are context IDs, not
  QWidget pointer arguments.
  Input processing at 0x144f8f020 branches on MouseButtonPress (2), FocusIn (8)
  and WindowActivate (24). Mouse/focus cases enter 0x144f903b0, which calls the
  context lookup at 0x144f8ea00. Window activation also reaches that lookup.
  The lookup walks registered entries in a QMap and calls QWidget::isAncestorOf
  on their widget pointers versus the incoming widget at 0x144f8eb23 and
  0x144f8ec67. Successful matches assign context IDs; the default is -1.
  An unmatched lookup causes the focus update at 0x144f903b0 to skip its normal
  update path. Window activation also has a separate-window context branch.
This is real binary evidence of the kind of context lookup previously only
hypothesized. A separate top-level host breaks ancestry to original page roots
under Qt's same-window rule even when its QObject parent chain is preserved.
The successful child-host result and lost spacebar targeting fit this mechanism.
However, the registered entry objects/IDs and branch outcomes have NOT been
captured live. This is a strong candidate for lost logical playback context,
not yet proof of the silence or waveform-stutter root cause.
