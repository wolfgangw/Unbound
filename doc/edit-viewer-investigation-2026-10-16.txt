Design implications / next experiments
------------------------------------
1. Whole-widget viewer reparenting is feasible for initial rendering and Program
   playback. It needs a dedicated session rather than transferring the Source
   QStackedLayout into an ordinary sidebar host.
2. Full Screen Timeline is evidence that Resolve already supports a viewer-free
   main layout, but invoking the complete action would impose Dual Screen and
   relocate unrelated panels. It is not yet a suitable automatic reclamation API.
3. Investigate the native layout manager/mode signal path before adding geometry
   interception. Do not guess OnSizeModeChanged(int) enum values or private offsets.
4. Distinguish Program-only, Source-only and both-floating cases. One remaining
   docked viewer should keep its region; only both floating can free the full
   vertical viewer area. Native single/dual mode and width changes need explicit
   behavior, including startup restoration when the Source pane is unavailable.
5. Test Source playback/audio, mode changes, clip loading, shortcuts, resizing,
   page return and native Dual Screen transitions in a fresh Resolve session.
   The current prototype deliberately does not persist geometry or docking.

On-disk Qt metadata identifies the actual menu receiver class:

  UiMainMenuSlots
    workspaceDualScreenOn_triggered(bool)                  local method 815
    workspaceDualScreenFullScreenTimeline_triggered(bool)  local method 816

The generated Qt dispatcher at 0x1452a4970 maps method 816 to 0x1452a1a40.
That handler passes the checked state to the native setter at 0x141008600.
The setter checks a native enablement condition, derives mode 1/2 from false/true,
updates native mode state, calls 0x1452e7a40, then refreshes the screen arrangement.
The mode routine's mode-2 branch applies the special mode to Edit (page key 3)
and resets other page arrangements through the same registry. This is a broader
workspace operation, not a visibility toggle for the viewer widget.

    OnAudioMixerCurrentWidthChanged(int)
    OnTimelineSplitterMoved()
    SetPlayerViewerExpanded(bool)

Its three paths correspond to the observed Single Screen, Dual Screen and
Edit Full Timeline arrangements (SSM, DSM, EFTM). Static branches use modes 0, 1,
2. A fresh-session metadata capture confirms this controller is a non-widget
child of the Edit conformer panel, alongside three UiLayout::UiDynamicLayout
objects. Those expose AnchorMoved(UiLayoutAnchor*,int), with no Qt methods for
removing an arbitrary region or selecting a layout mode. No mode enum is exposed
through these objects' Qt metadata.

Important distinction: UiResizeManager exposes SizeModeChanged(int), whereas
UiMultiScreenManager exposes ScreenModeChanged(). UiConformerPanelImp's
OnSizeModeChanged(int), 0x14113e380, forwards sizing to two child components and
calls UpdateViewerVisibility(), 0x14114d2b0. It does not set the screen mode.
The layout controller's OnScreenSizeModeChanged() similarly reacts to current
native state. Neither is an independent Full Screen Timeline selector.
SetPlayerViewerExpanded(bool) changes a separate viewer-expansion flag and
refreshes the existing single/dual layout; it does not select EFTM.

Current design assessment
-------------------------
We have identified and live-confirmed the native handler path. No separately
exposed Qt operation for collapsing the viewer region in ordinary Single Screen
mode has been established. Calling the entire native menu handler would impose
Dual Screen and its unrelated panel moves; calling a reaction slot cannot replace
the missing mode change. Calling the recovered private routines or patching
their fields would add version-specific binary dependencies and is not proposed.

Two viable investigation directions remain:
  - Inspect the native dynamic layout anchors/constraints for a reversible
    zero-height viewer region. GammaRay may help inspect these native objects,
    but no public Qt mutation interface has yet been found. This is a research
    lead, not a working solution; do not call OnAnchorMoved with invented pointers.
  - Prototype a narrowly scoped, reversible geometry adapter for the Edit viewer
    region and timeline, active only when all available viewers float. It must
    cooperate with native resize/sidebar/page/mode changes, preserve the native
    splitter state, and restore native behavior when either viewer docks. This
    would be explicit Unbound layout behavior, not reuse of native EFTM.

At this stage no production viewer feature or reclamation adapter was implemented. The
scope remains local development, with no release build, version/tag or ZIP.
After tracing, Dual Screen was turned off and the main window maximized again;
native viewers are docked and timeline position remains 00:00:52:07. Native mode
transitions changed timeline viewport/scroll presentation. The scoped trace is
stopped; the metadata/trace DLLs remain loaded until Resolve exits. GammaRay was
not required for this stage.

Layout anchors and constraints: deeper investigation
----------------------------------------------------
Same installed binary/hash and live PID 8720 as above. No private function was
called and no private state was written. The only layout changes were normal
mouse drags of Resolve's native viewer/timeline divider, subsequently restored.

AnchorProbe.dll subscribes to the public Qt signal
AnchorMoved(UiLayoutAnchor*,int) on the three Edit UiDynamicLayout objects.
All three connections succeeded. It records opaque anchor identities and native
region geometry; it never dereferences an anchor in Resolve. It stops after two
minutes or a second launcher invocation, disconnects only its own subscriptions,
and caps recording at 100 samples. This session was explicitly stopped.

The active Single Screen layout sender was 0x1fa31ff40f0. A drag of the divider
towards the top emitted anchor pointer 0x1fa31e4ecf0, requested position 134.
The viewer region stopped at height 319 and timeline started at y=320:

  frameEditPageWidgetsContainer: [0,36,1721,1278]
  frameEditPageVideoPlayers:     [0,0,1300,319]
  frameEditTimelinesHolder:      [0,320,1721,958]

These are logical Qt coordinates relative to each widget's parent. The main
window became 1721 pixels wide on activation, with native Single Viewer Mode;
the original Source stack was unavailable at that width. This test establishes
the native single-screen divider constraint, not behavior with both viewers
floating. Timeline position stayed 00:00:52:07. The viewer frame's QWidget
minimumSize was [0,0], as was the timeline holder's; Qt minimumSize is therefore
not the source of this clamp.

External ReadProcessMemory reads, bounded to the emitted anchor and its QString
name, established the object name timelineBarAnchor, native key 5, position 319
at the limit, and a false edge-anchor flag. After restoring the divider its
position was 643, close to the starting 644; a final one-pixel drag adjustment
was made. The external reads cannot invoke target code or dereference a bad
address inside Resolve. The diagnostic offsets are specific to this exact
binary and were not added to production code or the injected observer.

The anchor's vtable/RTTI confirms UiLayout::UiLayoutAnchor with no base classes.
In particular it is not a QObject. Its manager has only the inherited
objectName property, no dynamic properties, and the AnchorMoved signal; there
are no Qt setters for anchor limits, position, collapse, or region activity.
GammaRay's standard QObject property inspector therefore cannot expose these
private anchor fields as editable Qt properties. A more specialized native
debugger/type-aware inspector would be required to change them directly, which
would not provide a portable feature mechanism.

On-disk code confirms the clamp:
  UiConformerPanelLayout::OnAnchorMovedInSSM at 0x14115fc00 dispatches on
  the native anchor key. The key-5 path at 0x14115fd50 computes a lower bound
  max(native computed minimum, floor(0.25 * container height)). Its upper bound
  is based on 0.75 * height, additionally limited by space reserved below.
  The 0.25 and 0.75 constants were read directly from the binary. With height
  1278, floor(0.25 * 1278) is 319, exactly matching the live result. It updates
  the stored split ratio and position, then applies the native layout.

This is a stronger result than a widget minimum-size constraint: lowering the
QWidget minimum or requesting a zero splitter position will not bypass the
native handler's explicit nonzero lower bound in this arrangement. Other
anchors in this same handler use different limits (including the 370/440-pixel
constants seen earlier); those must not be attributed to timelineBarAnchor.

Internal collapse support DOES exist:
  A native diagnostic string identifies
  UiDynamicLayout::LayoutMultipleAnchorWidgets at 0x144eafec0.
  Its caller 0x144eb07f0 passes native region activation flags and anchor/widget
  lists. The routine selects active entries from that flag list and links or
  unlinks anchors accordingly; it is not driven by QWidget::isVisible().
  It also explicitly rejects attempts to collapse an outer edge anchor.
  Ordinary Edit layout preparation builds a list of 11 native region flags
  from native controls and page state, then applies it via 0x1411680c0.

Thus the engine has the capability we want, but the missing integration point
is a way to mark the viewer REGION inactive in that native policy. Detaching
the two inner viewer widgets, changing their Qt minimum sizes, or hiding the
outer QWidget does not supply that flag. Neither the manager's Qt metadata nor
the anchor object exposes an operation to do so. The generic collapse routine
is private machine code; its existence does not make it a reusable Qt API.

Assessment after anchor investigation
--------------------------------------
No safe native anchor/property shortcut has emerged. A private field patch or
direct call to recovered addresses would couple the feature to this binary's
class layouts and mode policy; neither was attempted or proposed for Unbound.
The practical next prototype remains an explicit reversible geometry adapter,
confined to the Edit viewer/timeline region while all available viewers float.
It should react to native layout events rather than poll or repeatedly force
anchor values, and preserve/restore the native split ratio and mode behavior.

Reversible geometry adapter prototype and live validation
---------------------------------------------------------
Implemented in tests/platforms/windows/viewer-probe/viewergeometryadapter.h and
connected to the existing local ViewerExperiment controls. This is separate from
the production controller, settings and release build. Build output for this
iteration is build/windows/viewer-adapter/Release/.

The adapter observes only the identified native Edit regions and page. Native
Move/Resize/Show/Hide events capture the latest native rectangles, and a coalesced
queued adjustment applies the expanded layout. Self-generated geometry events
are excluded. There is no recurring timer, discovery scan, fake native resize,
anchor write, minimum-size override or call to a recovered private address.
Page departure pauses the adapter and restores native geometry; return resumes
it. Reparenting a key native region disables it.

The native viewer container is kept explicitly shown at height zero, preserving
the floating hosts' native ancestry. The timeline expands upward within the
horizontal intersection of the native viewer and timeline rectangles. Full-height
side columns and their vertical handles extend downward; partial/stacked columns
retain native geometry. The native viewer/timeline divider is hidden only while
expanded. Docking restores saved native geometry and explicit visibility.

covered Inspector. That experiment was removed, docking both viewers, and Resolve
was restarted before testing the corrected central-column implementation.

2026-10-17: 005 failed live validation; early layout filtering
--------------------------------------------------------------
User confirmed 005 still flashes apparent space for the hidden Source viewer
and remains vertically unstable during main-window drag resizing. The earlier
plain-widget fixture did not model the actual nested Qt layout and was insufficient.

Qt 5.15.2 QApplicationPrivate::notify_helper calls application event filters,
then QLayout::widgetEvent, then receiver/object event filters, then QWidget's
event handler. Reference (inspection only; no Qt source copied into Unbound):
https://github.com/qt/qtbase/blob/v5.15.2/src/widgets/kernel/qapplication.cpp#L3353-L3383

005 filtered at the receiver level, after QLayout had already resized children.
The fixture now includes a real QVBoxLayout with a child viewport whose divider
clamps on shrink. This test FAILS against 005 with:
  Qt child layout processed the native shrink before the timeline object filter

The updated adapter filters the retained timeline's resize events at application
level, before QLayout, while preserving native baseline geometry. No work beyond
a quick event-type check is done on paint/input/playback events; no discovery or
polling is introduced. The application filter exists only while reclamation is on.

Native page/panel/root resize events are forwarded once through Qt under a scoped
recursion guard, then adapted geometry is applied synchronously on completion.
This avoids leaving the native viewer region/timeline rectangle in place until
a queued callback during interactive resizing. Nested native resize handlers run
normally inside that pass. Other activation/layout events remain coalesced.
Docking and page departure restore native geometry and deliver any pending resize.

The expanded fixture now passes with nested viewport preservation, consistent
oldSize/newSize, and synchronous reclaimed geometry before the native resize call
returns. It asserts that the native handler runs once, not twice. These results
justify internal 006 for fresh-session live validation; they do not establish
that all Resolve-specific resize behavior is fixed without that validation.
